## ГЛАВНЫЙ ФАКТ (доказан ledsim-трассой)
Scan-chain эмитится СТРОГО по порядку портов a=1..36 (LEDUP0; LEDUP1 — порты 37-72):
  00: ld a,1 ; 02-0A: for a=1..36 { b=2a+1; call 0x56 → push 1 бит; a++ } ;
  0C-12: инкремент фазы mem[0xF0] (0..4) ; 16: send 0x24 (=36 клоков) → halt.
0x56: tst (b),0x00; jnc 0x7f(push 0x0f)/jmp 0x83(push 0x0e) — 1 бит/порт, читает mem[2a+1].
=> порт a -> позиция a в цепочке. ДЫРКА НЕ СХЛОПЫВАЕТСЯ микрокодом. Значит −4 НЕ в порядке микрокода.

## Где тогда −4 (открытый вопрос)
- Микрокод читает бит порта из mem[2a+1] (НЕ 0x80+phys!). Наш SDK (counter.c:5675,
  soc_controlled_counters_collect64) пишет линк в 0x80+phys -> микрокод это НЕ читает.
- 3 C-правки (ledproc A0/обе ветки, counter.c) с +4 — 0 эффекта на панель (подтверждено бойнсом:
  реальные link-ячейки idx54/58, не совпадают ни с одним C-писателем). => LED горят от MAC-direct
  статуса (LINKUP доступен для XE/SERDES MAC, микрокод читает сам, без CPU).
- Противоречие: если микрокод ровный И читает MAC-direct по phys, то phys21->поз21 (ровно), а видим −4.
  Значит либо панель-разводка цепочки не 1:1 (но тогда сток тоже −4, а он «ровно»?), либо сток грузит
  ДРУГОЙ микрокод/портмап, либо «сток ровно» — неточное наблюдение. Модель неполна.

## УТОЧНЕНИЕ (ledsim OP_TST + hardware bounce) 2026-10-08
- `tst (b),0x00` (OP_TST): cflag = бит0 от mem[2a+1]. По ISA **bit0 = link up**. Значит микрокод:
  линк позиции a = бит0 в DATA_RAM[2a+1]. Микрокод-память mem[X] == devmem idx X (база LEDUP0 0x1400,
  REG×4: 0xc0001400+4*X). => микрокод читает линк позиции a из devmem idx (2a+1), нечётные 3..73.
- Цепочка ровная (позиция a→панель a). Если бы CPU писал линк phys21 в idx(2*21+1)=43, панель=21.
  −4 => линк phys21 пишется в слот позиции 17 = idx(2*17+1)=35 (dense/компакт).
- ПРОТИВОРЕЧИЕ (не закрыто): bounce xe16(phys21) реально дёргает **idx58 и idx112** (ЧЁТНЫЕ!),
  xe18(phys23)→idx54+112. Это НЕ odd-слоты 2a+1 и НЕ counter.c(0x80+phys=149) и НЕ ledproc(0xa0+phys=181).
  Кто пишет idx54/58 — НЕ установлено. Либо микрокод-память читается иначе (не mem[X]=idx X), либо
  слоты активности (2a, чётные) а не линка, либо ещё один писатель. МОДЕЛЬ НЕПОЛНА.

## Реальный кандидат-фикс (на след. заход, БЕЗ пересборки bcm.user!)
Раз микрокод читает линк из DATA_RAM по позиции, а не из MAC — можно **Linux-side демон** (как
box-leds.sh): периодически читать линк (через FIFO `ps` или сам DATA_RAM) и писать правильные биты
в DATA_RAM[2*phys+1] (devmem), т.е. в слот позиции = phys (а не dense-rank). Это чинит −4 без
трогания bcm.user. СНАЧАЛА: закрыть противоречие idx58/112 (bounce-калибровка всех 3 портов +
сверка с mem[2a+1]-моделью через ledsim с реальными data).

## ЧИСТАЯ bounce-калибровка 2026-10-08 (коробка в норме, CTRL0=0xB3)
Гашение каждого up-порта → единственная per-порт ячейка (up=1,down=0):
  phys6(xe5)->idx37->панель6 ; phys21(xe16)->idx52->панель17 ; phys23(xe18)->idx54->панель19.
  (idx112 — общий агрегат, шум.)
=> idx = phys+31 ЧЁТКО. Панель = idx-31 (phys<=16) или idx-35 (phys>=21) = dense-rank (phys минус дырка).
   Это ТА ЖЕ первая калибровка (idx=phys+31). Значит микрокод читает линк из idx(phys+31) и выводит
   на панель по dense-rank -> −4 для phys>=21.

## ПОЧЕМУ devmem-записи в эти ячейки НЕ зажигают (ключ, подтв. 2 раза)
Писал 0x01 в idx56 (ночь) и в нечётные 43/51/61 (утро) — НОЛЬ эффекта. Вывод: **микрокод САМ
рефрешит idx(phys+31) из MAC-линка каждый цикл (~30Гц)** -> наша devmem-запись затирается до вывода.
Значит CPU (ни bcm.user, ни Linux-devmem) НЕ может повлиять через эти ячейки. Подтверждает: линк берётся
MAC-direct, −4 зашит в ВЫВОДНОМ позиционировании микрокода (dense-rank), а НЕ в данных.

## ОТКРЫТОЕ ПРОТИВОРЕЧИЕ (для след. раза)
ledsim говорит вывод РОВНЫЙ (позиция a=1..36 -> панель a, phys21->панель21). Железо даёт −4
(phys21->панель17 = dense-rank). Значит либо (а) ledsim-модель вывода не совпадает с hardware-чейном
(дырочные позиции не эмитятся / чейн физически плотный), либо (б) hardware-чейн пропускает dark-позиции
17-20. Если (б) — то и СТОК был бы −4; но заметка говорит «сток ровно» (возможно, неточно — ПЕРЕПРОВЕРИТЬ
под стоком: воткнуть модуль в cage21 под netdevd и глянь панель).
