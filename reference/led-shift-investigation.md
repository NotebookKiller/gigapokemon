# LED −4 сдвиг — расследование (2026-10-05, НЕ РЕШЕНО)

Симптом: модуль в cage N (phys N) зажигает диод на позиции N−4 для phys≥21.
Проверено глазами на железе:

| soft | phys | cage | горит LED | сдвиг |
|------|------|------|-----------|-------|
| xe5  | 6    | 6    | 6         | 0 ✓   |
| xe16 | 21   | 21   | 17        | −4    |
| xe18 | 23   | 23   | 19        | −4    |
| xe43 | 48   | 48   | 44        | −4    |

Ровно −4 для phys≥21 (дырка phys17-20: portmap_16=16 → portmap_17=21, phys 17-20 не замаплены).

## Что ТОЧНО установили (devmem, калибровка)
- LED DATA_RAM читается `busybox devmem` (НЕ `devmem` — не в PATH!). BAR свитча 0xc0000000
  (устр. 01:00.0), подтверждён /proc/iomem. База сканов: b0=0xc0001400 (LEDUP0), 0xc0002400 (LEDUP1).
- Статус живого порта = `0x00000001` в ячейке. Калибровка (гашение xe16 → очистилась idx52):
  **phys6→idx37, phys21→idx52, phys23→idx54** ⇒ idx = phys+31 (хранится по СЫРОМУ phys, дырка
  в RAM НЕ схлопнута). Значит −4 делает **микрокод/разводка** на этапе RAM→диод (dense-pack).
- `linkscan=off` → ВСЕ диоды горят (артефакт: без свежего статуса микрокод зажигает всё). Поэтому
  замороженным линксканом свип НЕ сделать.
- **devmem-ЗАПИСЬ в RAM не меняет диоды** — микрокод латчит статус по механизму обновления
  линкскана (soc_pci_write из коллбэка), а не по сырому значению ячейки. Все мои devmem-write тесты
  (idx56 и т.п.) были невалидны. ⇒ проверить фикс можно ТОЛЬКО пересборкой.
- Ранняя ошибка: писал `0x000014e0` вместо `0xc00014e0` (забыл базу BAR) — несколько раундов впустую.

## Активный писатель статуса
- `src/appl/diag/ledproc.c: ledproc_linkscan_cb` (line 253) — регистрируется `bcm_linkscan_register`
  при `led auto on` (его делает box-leds.sh). ЭТО активный путь (idx52 меняется при линк-ап/даун).
- НЕ `counter.c:5675` (там byte=0x80+phy_port; пробовал — 0 эффекта, откатил).
- Для TD_TT в ledproc есть `if(soc_feature_led_data_offset_a0){...A0-ветки...} else {0x80+phy_port}`.
  TD2-ветка делает `byte = 0xa0 + phy_port − skip_count` (ВЫЧИТАЕТ). Наш 56840 идёт в else-ветки.

## ГИПОТЕЗЫ почему правки ledproc не сработали (для след. сессии, коробка будет включена)
1. **skip_count = 0**: port_p2l_mapping[17..20] НЕ == −1 (SDK хранит дырку иначе). → добавить в
   ledproc_linkscan_cb временный `printk("LEDDBG port=%d phys=%d skip=%d byte=%d\n",...)`, собрать,
   глянуть в bcmrun.log реальные phys/skip/byte. Это РЕШИТ вопрос за один заход.
2. **`led auto on` ведёт в ДРУГОЙ путь**: box-leds.sh может ставить аппаратный LED-режим, где
   статус пишет микрокод/железо из PHY-регистров, а не CPU-коллбэк. Тогда idx52-изменение — не от
   ledproc_linkscan_cb. Проверить: временно убрать ledproc_linkscan_cb (или printk) — меняется ли RAM.
3. **Фикс в мёртвой ветке из-за soc_feature**: не добили, какую ветку (A0/не-A0) реально берёт 56840.
   printk из гип.1 заодно покажет (добавить маркер в каждую ветку).
4. **Правильный путь — микрокод**: если CPU вообще не пишет per-port статус, править надо
   LED-микрокод (box-leds.sh) — таблицу порядка портов. Дизассемблировать микрокод.

## ОБНОВЛЕНИЕ 2026-10-07 (инсайт пользователя — вероятно корень)
Пользователь заметил: почему наш код (TD-else) сделан через цикл `port_p2l_mapping[i]==-1`
(как TD2), а не как **Helix4/Triumph3**, которые правят phy_port/byte **жёстко зашитыми
константами** (Helix4: `phy_port-=4` при phys>52; Triumph3: `byte+=12`@37, `-=4`@>=38, `+4`@led_ix)?
Вывод: наш фикс дал РОВНО 0 изменений (диоды не шевельнулись даже не туда) ⇒ `skip_count==0` ⇒
на нашей коробке `port_p2l_mapping[17..20]` НЕ равны −1 (дырка хранится иначе). TD2-цикл молча стал
no-op. Helix4/Triumph3 потому и хардкодят — чтобы не зависеть от p2l. Это объясняет ВСЕ 3 провальных
билда (все использовали p2l-цикл в активной ветке или били мимо ветки).
ФИКС (собран, НЕ задеплоен — ждёт SSH): bins/bcm.user.ledfix-hardcoded.gz (md5 d6ed6577). Обе
else-ветки переписаны хардкодом: `byte = A0 + phy_port; if(led_ix) byte+=4; else if(phy_port>=21) byte+=4;`
+ точечный `printk("LEDDBG a0/na phys=%d led_ix=%d phy_port=%d byte=%d")` для phys==21 (xe16).
При деплое: `grep LEDDBG /tmp/bcmrun.log` покажет (1) какая ветка реально исполняется, (2) byte —
подтвердит, что код отрабатывает; диоды РЕАЛЬНО сдвинутся (хардкод не зависит от p2l) → увидим,
+4 туда или надо −4 (ЗНАК ВСЁ ЕЩЁ НЕ ПОДТВЕРЖДЁН — панель ни разу не двигалась). Если не туда — 1 строка.

## Быстрый план на след. заход (коробка включена, 1 пересборка)
Вставить printk с phys/skip/byte/ветка в ledproc_linkscan_cb + аналогичный маркер в counter.c LED,
собрать, задеплоить, `grep LEDDBG /tmp/bcmrun.log`. Это за один цикл скажет: исполняется ли код,
чему равен skip, какая ветка. Дальше точечно.

Девмем-карта диодов (для ручной проверки без пересборки, статус живого порта, НЕ для записи):
LEDUP0 phys P: читать `busybox devmem $((0xc0001400 + 4*(P+31)))` (=0x1 если линк-ап). LEDUP1 (P>36):
база 0xc0002400, но калибровки LEDUP1 нет (не было живого порта phys≥37).
