## Что сделали

### Автозапуск (прописан в inittab, проверен ребутами)
Коробка на каждом ребуте возвращалась в штатный GigaVUE-OS. Прописали автозапуск через `/etc/inittab`
(он на rootfs `mmcblk0p5`, ro при работе → правка через `mount -o remount,rw /`; переживает ребут):
```
ac:3:once:/var/bcm/boot.sh       # сеть + доступ (watchdog)
fn:3:respawn:/var/bcm/fans.sh    # тихие вентиляторы
bx:3:once:/var/bcm/box-start.sh  # автозапуск bcm.user — за kill-switch /var/bcm/DISABLE
```
Скрипты — на разделе VAR (`/var/bcm`, rw, персистентный).

### Самолечащийся доступ (`boot.sh` → watchdog)
GigaVUE **пересобирает `passwd/shadow` из своей конфиг-базы на каждом boot'е** и затирает нашего юзера `op`
(а штатный статик 10.101.120.35/28 — чужая подсеть). Одноразовый скрипт проигрывал гонку с этой пересборкой.
Решение — `boot.sh` сделан **вечным watchdog'ом** (цикл 30с): держит `op`+ключ и, если eth0 не в нашей
сети 10.156/22, переполучает DHCP. Проверено ребутом: доступ по SSH возвращается **без serial** (~3–5 мин
на самолечение после ребута — норма из-за медленной загрузки GigaVUE).

## Инцидент и уроки (стоили нескольких ребутов)
- **`kill -CONT pm` при мёртвом netdevd РЕБУТИТ коробку** — pm как watchdog видит пропажу netdevd и
  передёргивает систему. Пока pm заморожен (`kill -STOP`) — SSH живёт часами. Восстановление чипа после
  ручного эксперимента — только через reboot, НЕ через CONT pm.
- **При замороженном pm обычный `reboot` НЕ срабатывает** (идёт через pm/mgmtd) — нужен **`reboot -f`**.
- **Порядок работ:** автозагрузку СЕТИ впаивать первой — тогда любой ребут возвращает SSH сам.

## Главное — разбор зависания `init bcm`
- Потерянный `init mmu` (регрессия в rc.soc) — вернули. Полная рабочая последовательность:
  `init soc → init misc → init mmu → init bcm → port xe enable=true stp=forward an=on → linkscan → port xe linkscan=on`.
- Но init **флейкует ~1/2–1/3**: тихо виснет в ioctl после `init soc` (инициализация таблиц).
- **Корень (сравнение с netdevd):** netdevd поднимает чип через **linux-kernel-bde с реальным MSI-IRQ 23**
  (на коробке ~3.2М прерываний) + DMA 256M → завершения DMA приходят мгновенно. Наш bcm.user открывает
  `/dev/linux-user-bde` + `/dev/mem` (PIO-mmap), HW-прерывания в процесс **не доходят** (ими владеет
  kernel-bde) → работает в `polled_irq_mode=1` (ipoll опрашивает CMIC). **DMA-пул есть** (64МБ), но
  **сигнализация завершения** через ipoll — с гонкой → зависание. `polled_irq_delay` уже 0 (потолок polled).
- **PIO-обход** (`mem_clear_hw_acceleration=0`, `table_dma_enable=0`, `tslam_dma_enable=0`) — тупик:
  медленно + падает в assert `sal_mutex_take: (rm)` (sync.c:572). Откатили.

## План на следующий заход — настоящий DMA через реальный IRQ
Дать bcm.user реальный MSI-IRQ 23, как у netdevd:
1. kill netdevd → **перезагрузить BDE-модули** (`rmmod` knet/user_bde/kernel_bde → `insmod` заново, как
   `/sbin/load_bcm.sh`) — освобождает IRQ.
2. Запустить bcm.user с **`polled_irq_mode=0`** → `soc_cm_interrupt_connect` возьмёт IRQ свежим → реальные
   прерывания → DMA-завершения мгновенно → init быстрый и без флейка. Затем снять `DISABLE`.
